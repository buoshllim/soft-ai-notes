# CLAUDE.md 잘 쓰는 법

CLAUDE.md에 뭘 적느냐에 따라 Claude가 일하는 방식이 꽤 달라짐. 오래 쓰면서 남겨두면 실제로 효과 있었던 내용들 정리.

---

## 1. 개발 순서 정해주기

아이디어가 생겼을 때 무작정 "만들어줘"부터 시작하면 방향이 산으로 가는 경우가 있음. 아래처럼 순서를 적어두면 Claude가 먼저 요구사항을 물어보고 정리한 다음 개발을 시작함.

```md
## 개발 순서

새로운 무언가를 만들기 시작할 때는 아래 순서를 따른다.

1. 아이디어 구체화 — 요구사항 인터뷰부터. 모호한 게 있으면 물어봐.
2. BRD — 왜 만드냐, 누가 쓰냐, 뭘 해결하냐 (두 줄이라도)
3. 기능 스펙 정리 — 파일 구조, 작업 단계 정의
4. 개발
```

"만들어줘"라고 하면 Claude가 먼저 질문하고 정리한 다음 코드를 씀. 이 순서를 안 적어두면 바로 코드부터 씀.

---

## 2. 코딩할 때 행동 원칙 (Andrej Karpathy 스타일)

"코드 잘 짜줘"보다 구체적인 원칙을 적어두는 게 효과적임. 아래 내용을 그대로 붙여넣거나 필요한 것만 골라서 써도 됨.

```md
## 코딩 원칙

### 코딩 전에 생각하라
- 가정이 있으면 먼저 말해. 불확실하면 물어봐.
- 여러 해석이 가능하면 제시해. 침묵 속에 선택하지 마.
- 더 단순한 접근이 있으면 먼저 말해.

### 단순하게 유지
- 요청한 것 이상의 기능 추가 금지.
- 한 번만 쓸 코드에 추상화 금지.
- 200줄로 짤 수 있는 걸 400줄로 쓰지 마.

### 외과적으로 변경
- 반드시 필요한 것만 건드릴 것.
- 멀쩡한 코드를 리팩토링하지 마.
- 내가 만든 불필요한 import, 변수는 제거. 원래 있던 죽은 코드는 손대지 마.
```

적어두지 않으면 Claude가 요청하지 않은 기능을 추가하거나, 인접한 코드까지 손대는 경우가 생김.

---

## 3. 최종 검토 기준

"검토해줘"라고 할 때 막연하게 보는 게 아니라 네 가지 관점으로 보게 할 수 있음.

```md
## 최종 검토 기준

"검토해줘" 요청이 오면 아래 4가지 관점으로 확인한다.

1. 부수 효과 — 이 변경이 다른 기능에 영향을 주는가?
2. 예외 상황 — null, 빈값, 네트워크 오류 등 외부 변수에 견고한가?
3. 기술 부채 — 3개월 뒤 내가 한눈에 이해할 수 있는가?
4. 논리 완결성 — 요구사항과 최종 결과 사이에 괴리가 없는가?

진짜 없으면 "이상 없다"고 말해도 됨. 형식적 확인만 하고 끝내지 말 것.
```

코드를 짜고 나서 "검토해줘"라고 치면 이 네 가지를 기준으로 스스로 점검하고 알려줌.

---

## 4. 응답 방식 조절

Claude는 기본적으로 답변이 길고 형식적임. 아래처럼 적어두면 불필요한 설명이 줄어듦.

```md
## 응답 방식

- 기본은 짧게. 불릿·헤더는 정말 복잡한 내용일 때만 사용.
- 간단한 질문엔 몇 문장으로 끝낼 것.
- 마지막에 "이렇게 했습니다" 요약 반복하지 마. 내용만.
- 최신 버전·현재 가격·지금 동향 같은 질문은 묻지 말고 즉시 검색.
```

이거 적어두면 쓸데없는 줄이 확 줄어듦.

## 5. 파일 관리 원칙

프로젝트가 커지면 문서, 기획, 코드가 뒤섞이는 경우가 있음. 미리 정해두면 나중에 찾기 편함.

```md
## 파일 관리

- 개발 프로젝트 문서 (스펙, DB 설계 등) → {프로젝트}/docs/
- 기획·전략 문서 → 별도 노트 앱이나 프로젝트 외부 폴더
- 코드·실행 파일 → {프로젝트}/ 에만
```
